# Release

How a version tag becomes the artifacts a user installs. The workflow is
[release.yml](../.github/workflows/release.yml), generated by
[cargo-dist](https://axodotdev.github.io/cargo-dist/) from
[dist-workspace.toml](../dist-workspace.toml). The product side of this - what
a user downloads and runs - is [docs/installation.md](../docs/installation.md).

## Trigger

Push a tag that names the version in `Cargo.toml`:

```text literal
git tag v0.1.0
git push origin v0.1.0
```

A tag with a prerelease suffix produces a prerelease. The workflow's `plan`
job also runs on every pull request, so a configuration error fails the pull
request instead of the release.

## What it builds

| Target | Artifact |
|---|---|
| `x86_64-unknown-linux-gnu` | `buzzx-x86_64-unknown-linux-gnu.tar.xz` |
| `aarch64-apple-darwin` | `buzzx-aarch64-apple-darwin.tar.xz` |
| `x86_64-apple-darwin` | `buzzx-x86_64-apple-darwin.tar.xz` |
| `x86_64-pc-windows-msvc` | `buzzx-x86_64-pc-windows-msvc.zip` |

Each archive holds the binary and the README and carries a `.sha256` file
beside it. The release adds the two installers (`buzzx-installer.sh`,
`buzzx-installer.ps1`), a `sha256.sum` over everything, and the source
tarball. The builds use the `dist` profile, which inherits `release`.

Adding a target is one line in `dist-workspace.toml` plus a release: an
`aarch64-unknown-linux-gnu` artifact is a decision about which users to serve,
not a code change.

## Rules this repository adds to the generated workflow

- Every action is pinned to a commit. `dist` writes those pins from
  `[dist.github-action-commits]` in `dist-workspace.toml`, so they survive
  regeneration; the version each commit names is the comment beside it there.
  This is the rule [ci.yml](../.github/workflows/ci.yml) follows, with the
  version comment in the config instead of beside the pin.
- The workflow holds `contents: write` and no other secret. It creates the
  release with the workflow's own token; nothing else is stored.
- The release is unsigned. SmartScreen and Gatekeeper warnings are documented
  for the user in [docs/installation.md](../docs/installation.md); removing
  them needs a paid certificate and is a separate decision.

## Regenerating

`dist plan` fails when the generated workflow is out of date with the config,
and that failure is a pull request failure, not a release failure. After
changing `dist-workspace.toml`:

```text literal
dist generate
dist plan
```

The pinned `cargo-dist-version` in `dist-workspace.toml` is the version CI
installs, so a regeneration with a newer local `dist` shows up as a diff
rather than as a surprise at tag time.

## What a release does not prove

It proves the four targets build, the archives are shaped correctly, and the
checksums match. It does not run `buzzx`. The live-relay acceptance run stays
a manual step, exactly as it does for CI: see
[testing.md](testing.md) and the verification list in
[AGENTS.md](../AGENTS.md).
