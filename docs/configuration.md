# Configuration

`buzzx` needs two things to start: an identity and a relay. Both come from the
environment, flags, or a config file, in that order.

## Identity

The identity is one Nostr keypair. It is never generated by `buzzx`. The key
comes from one of three sources. First, the `BUZZ_PRIVATE_KEY` environment
variable, for example `export BUZZ_PRIVATE_KEY=nsec1...`. Second, the
`--private-key` flag, for example `buzzx tui --private-key nsec1...`. Third,
the `private_key` field of `~/.config/buzzx/config.toml`.

The key is a 64-character hex string or an `nsec1...` bech32 string. `buzzx`
accepts both, the same way the `buzz` CLI does.

Flags override the environment, which overrides the file. When no source has a
key, `buzzx` exits with code 3 and a message naming the sources it checked.

The private key is the identity. Anything `buzzx` signs is signed as that
identity, on every surface, including destructive operations. There is no
confirmation before a delete for this reason: the alternative is a prompt that
a script cannot answer.

### File permissions

`~/.config/buzzx/config.toml` holds a private key, so `buzzx` refuses to read
it when it is readable by other users. `buzzx init` writes the file with mode
0600. An existing file with looser permissions is reported and not read.

The environment variable is preferred over the file precisely because it keeps
the key out of the filesystem.

## Relay

The relay URL comes from one of three sources. First, the `BUZZ_RELAY_URL`
environment variable, for example `export BUZZ_RELAY_URL=https://relay.example`.
Second, the `--relay` flag, for example `buzzx tui --relay relay.example`.
Third, the `relay_url` field of the config file.

The default is `http://localhost:3000`. The value may be any of:

- `http://host:port` - used for the HTTP bridge; also converted to `ws://`.
- `https://host:port` - converted to `wss://` for the WebSocket.
- `ws://host:port` - accepted and converted to `http://`.
- `wss://host:port` - accepted and converted to `https://`.

A trailing slash is removed. A missing scheme is an error, not a guess,
because guessing the wrong scheme produces a confusing refusal from the relay.

The community boundary comes from the relay host. One identity on two relay
hosts is two communities. `buzzx` connects to exactly one relay per run; it
does not aggregate.

## NIP-OA auth tag

An agent identity that acts on behalf of an owner carries a NIP-OA `auth` tag.
`buzzx` supports it with the same contract the `buzz` CLI uses. The tag comes
from one of three sources. First, the `BUZZ_AUTH_TAG` environment variable, for
example `["auth","<owner>","<conditions>","<sig>"]`. Second, the `--auth-tag`
flag with the same JSON. Third, the `auth_tag` field of the config file.

When set, the tag is attached to every signed event and sent as an
`x-auth-tag` header on HTTP requests. When it is absent, `buzzx` signs as the
identity alone, which is what a human identity needs.

`buzzx` verifies the tag against the identity's own pubkey at startup and
refuses to run with a tag that does not verify. A stale or revoked tag is the
most common cause of a 403 from the relay, and it fails fast here instead of
on the first write.

## Config file

The file lives at `~/.config/buzzx/config.toml`. All fields are optional.

```toml
relay_url = "https://relay.example"
private_key = "nsec1..."
auth_tag = "[\"auth\",\"<owner>\",\"<conditions>\",\"<sig>\"]"
```

There is no `default_channel` and no keybinding configuration in the first
phase. Both are settings that a single-operator tool does not need, and a
config file that carries them invites a second source of truth for behavior
that the keys already define.

`buzzx init --relay <url> --private-key <nsec>` writes the file, creates the
directory with mode 0700, and sets the file to 0600.

## Environment reference

`buzzx` reads these variables and no others. Config that changes behavior
belongs in flags, so a running session's behavior is visible in its command
line.

- `BUZZ_RELAY_URL` sets the relay base URL.
- `BUZZ_PRIVATE_KEY` sets the identity key, hex or nsec.
- `BUZZ_AUTH_TAG` sets the NIP-OA auth tag JSON.
- `BUZZX_CONFIG` overrides the config file path.
- `NO_COLOR` disables color in the TUI.
- `TERM` is read for capability detection. The value `dumb` disables the TUI.

## Exit codes

Every subcommand uses the same codes, matching the `buzz` CLI. Code 0 is
success. Code 1 is bad input, before any network call. Code 2 is a relay
unreachable or network failure. Code 3 is an authentication or identity
failure. Code 4 is another failure. Code 5 is a write conflict.

The TUI exits 0 on a clean quit and 3 when the relay refused the identity.
The TUI does not use the other codes: it is interactive, and its failures
appear on the status line rather than in an exit code.
